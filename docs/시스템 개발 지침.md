# 배드민턴 클럽 매칭 시스템 개발 지침 (AI 필수 준수사항)

## 0. 공통 최우선 원칙

- 모든 의사결정에서 **성능을 최우선 기준**으로 삼는다. 기획, 디자인, 프론트엔드, 백엔드, DB 각 단계에서 "더 예쁘지만 느린 방식"과 "덜 화려하지만 빠른 방식" 중 선택해야 한다면 반드시 후자를 택하고, 그 이유를 주석이나 커밋 메시지에 남긴다.
- 자동매칭 엔진, ELO 계산, 실시간 현황판 갱신처럼 사용자가 체감하는 지연이 UX를 직접 해치는 기능은 특히 응답 속도를 최우선으로 설계한다.
- 임의로 기능을 추가하거나 축소하지 않는다. 아래 명세에 없는 기능이 필요하다고 판단되면, 먼저 질문하고 확인받은 뒤 진행한다.
- 모호하거나 누락된 요구사항을 발견하면 추측으로 구현하지 말고, 반드시 먼저 질문한다.

---

## 1. 기획(Planning) 역할 필수 준수사항

- 작업을 시작하기 전, 아래 핵심 도메인 규칙이 요구사항에 모두 반영되어 있는지 빠짐없이 점검한다: 운영진/회원 권한 분리, 성별 색상 구분(형광펜 느낌), 콕 제출 현황 팝업, 드래그 앤 드롭 수동매칭, 퇴장 처리, 체육관 도착/게임중/대기/휴식 4단계 인원 상태, 코트 최대/사용중/미사용 구분 및 활성화·비활성화, 게스트 즉석 등록, 급수 8단계(S/A/B/C/D/E/F/G), 연령대 7구간, 여성 2급수 하향 보정, 연령대 가점(한 단계당 반급수=ELO 50점 기준), ELO 공식 기반 점수 변동, 승패만 기록(스코어 미기록), 자동매칭 9단계 우선순위, 자동매칭 제안(Draft)→멤버 바꾸기→확정(Confirm) 3단계 플로우, 코트 투입 후 멤버 바꾸기 불가 및 전원미배정 규칙, 예약매칭(대기열 4인 미만 시 자동 활성화), 정모 종료 시 승률 기반 결과 화면, 매월 1일 기준 월간 랭킹 등락 화면, 게스트 ELO 비영구 보존, 모임 홈 화면 정식 회원 전용 상시 랭킹.
- 새로운 기능이나 화면을 설계할 때는 반드시 "이 기능이 기존의 어떤 규칙과 충돌하지 않는지"를 교차 점검한 뒤 진행한다. 예를 들어 새 기능이 게스트 데이터 처리 정책이나 자동/수동 매칭 혼용 플로우를 깨뜨리지 않는지 확인한다.
- 각 기능 명세마다 예외 케이스(인원 부족 시 강제 매칭, 코트 전부 사용 중일 때 예약매칭 동작 등)를 함께 정의하고, 누락된 예외가 있으면 구현 전에 반드시 질문한다.
- 수치 기반 설정값(급수-ELO 환산 기준, 연령 가점표, K-factor, 예약매칭 임계 인원 수 등)은 하드코딩하지 않고 운영진이 조정 가능한 설정 값으로 다룬다는 전제를 항상 유지한다.

## 2. 디자인(UI/UX) 역할 필수 준수사항

- UI는 항상 **단순함(Simplicity)**을 최우선으로 한다. 한 화면에 너무 많은 정보나 버튼을 동시에 노출하지 않고, 정보 위계를 명확히 나누어(핵심 정보 → 보조 정보 → 상세 정보) 단계적으로 보여준다.
- 톤앤매너는 **트렌디한 감성**을 유지한다. 과도하게 올드한 버튼 스타일, 투박한 그림자, 불필요한 테두리를 지양하고, 여백(화이트스페이스)을 충분히 활용한 미니멀한 카드형 UI, 부드러운 라운드 처리, 적절한 마이크로 인터랙션(호버, 트랜지션)을 사용한다.
- 성별 구분 블록은 "형광펜 느낌"이라는 요구사항에 맞게 과포화된 원색이 아니라 하이라이터처럼 반투명하고 채도 높은 파스텔 계열 색상을 사용한다(예: 연한 핑크 계열과 연한 블루/민트 계열).
- 자동매칭 제안 카드, 대기열 카드, 코트 상태 카드 등 핵심 운영 화면의 정보 밀도는 "한눈에 파악 가능한 수준"을 기준으로 설계하며, 상세 정보(매칭 근거 등)는 클릭 시 펼쳐지는 방식으로 숨겨둔다.
- 1920×1080, 2560×1440, 모바일, 아이패드 프로/에어, 갤럭시탭 등 모든 기기에서 레이아웃이 깨지지 않도록 반응형 브레이크포인트(모바일 360~480px, 태블릿 세로 768px, 태블릿 가로 1024~1366px, 풀HD 1920px, QHD 2560px)를 기준으로 설계하고, 운영 화면은 좁은 화면에서 탭 전환/아코디언 형태로 재구성한다.
- 드래그 앤 드롭 인터랙션은 데스크톱 마우스 드래그와 모바일/태블릿 터치 드래그(long press 후 드래그) 모두에서 동일하게 동작하도록 설계하고, 터치 영역 크기를 충분히 확보한다.
- 디자인 시안을 결정하기 전, 유사한 트렌디 레퍼런스(최신 SaaS 대시보드, 스포츠 앱 등)의 패턴을 우선 참고하되, 과도한 애니메이션으로 성능을 해치지 않는 선에서만 적용한다.

## 3. 프론트엔드(React/Next.js) 역할 필수 준수사항

- 컴포넌트는 **재사용 가능한 컴포넌트(Reusable/Common Components)**와 **특정 화면 전용 컴포넌트(Page-specific Components)**를 명확히 구분하여 디렉토리 구조부터 분리한다. 예: `components/common/`(Button, Modal, Badge, Card 등 범용 UI)과 `components/features/matching/`, `components/features/ranking/`처럼 도메인별 전용 컴포넌트 폴더를 나눈다.
- 회원 블록, 매칭 카드, 코트 카드처럼 여러 화면에서 반복적으로 쓰이는 UI는 반드시 공통 컴포넌트로 추출하고, props를 통해 성별 색상·게스트 배지·급수 표시 등의 변주만 제어하도록 설계한다.
- 자동매칭 제안 상태(Draft)와 확정 상태(Confirmed)처럼 동일 데이터지만 상태가 다른 UI는 하나의 컴포넌트에서 상태(state)에 따라 분기 렌더링하도록 구성하여 중복 코드를 최소화한다.
- 실시간성이 중요한 화면(체육관 현황판, 코트 운영 화면, 대기열)은 불필요한 리렌더링을 방지하기 위해 상태 관리 범위를 최소 단위로 쪼개고(예: 전역 상태와 로컬 상태를 명확히 구분), 메모이제이션(`useMemo`, `useCallback`, `React.memo`)을 적극 활용해 성능을 확보한다.
- 서버 데이터 패칭은 Next.js의 서버 컴포넌트/클라이언트 컴포넌트 특성을 고려해, 초기 로딩이 중요한 정적성 화면은 SSR로, 실시간 갱신이 필요한 화면(현황판, 코트 상태)은 CSR 기반 폴링 또는 웹소켓으로 구분하여 구현한다.
- 드래그 앤 드롭 기능은 성능과 접근성을 모두 고려한 라이브러리(dnd-kit 등)를 사용하며, 터치 디바이스 대응을 기본값으로 설정한다.
- 타입 안정성을 위해 TypeScript를 전제로 하며, API 응답 타입은 백엔드 DTO와 1:1로 대응하는 타입 정의를 별도 파일로 관리한다.

## 4. 백엔드(Spring Boot) 역할 필수 준수사항

- 반드시 **MVC 패턴을 준수**하며, 계층은 `Controller → Service(인터페이스) → ServiceImpl(구현체) → Repository(JPA) / Mapper(MyBatis)`로 명확히 분리한다. Controller에는 비즈니스 로직을 절대 두지 않고 요청/응답 처리와 검증(또는 검증 위임)만 담당한다.
- Service는 반드시 인터페이스로 선언하고, 실제 구현은 `~ServiceImpl` 클래스에 작성한다. Controller와 다른 Service는 구현체가 아니라 인터페이스에 의존하도록 한다(의존성 역전 원칙 준수).
- 데이터 접근은 기본적으로 **JPA**를 사용하되, 복잡한 조인/집계 쿼리나 성능이 민감한 조회(자동매칭 후보 탐색, 랭킹 집계, 통계성 조회 등)는 **MyBatis**로 네이티브 쿼리를 작성해 성능을 확보한다. 단순 CRUD는 JPA, 복잡한 성능 critical 쿼리는 MyBatis로 역할을 분담한다.
- 자동매칭 9단계 우선순위 로직은 별도의 도메인 서비스(`MatchingEngineService` 등)로 분리하여, 각 단계(입장순서, 게임횟수 보정, 희망인원, ELO 밸런스, 파트너 지정, 기피인원 회피, 최근 동반자 회피, 강제매칭)를 독립적인 메서드 또는 전략(Strategy) 패턴으로 구현해 테스트와 유지보수가 용이하도록 한다.
- ELO 계산 로직은 별도의 유틸리티/도메인 서비스(`EloCalculator` 등)로 분리하여 어디서든 동일한 공식을 재사용하도록 하며, 급수-ELO 환산 기준·K-factor 등은 `club_settings` 테이블 값을 주입받아 사용하고 하드코딩하지 않는다.
- 게스트와 정식 회원을 다루는 로직은 공통 인터페이스(`SessionParticipant` 추상화 등)로 통합 처리하여, 매칭 엔진이 두 유형을 분기 처리하지 않도록 설계한다.
- 자동매칭 결과가 DRAFT 상태에서는 실제 ELO나 게임 횟수에 영향을 주지 않도록, 확정(Confirm) API가 호출되기 전까지는 트랜잭션을 커밋하지 않거나 임시 테이블/세션 영역에만 반영한다.
- 트랜잭션 경계는 Service 계층에서 명확히 관리하고(`@Transactional`), 승패 입력처럼 ELO 갱신이 동시다발적으로 일어날 수 있는 구간은 동시성 문제(동시 업데이트로 인한 데이터 정합성 깨짐)를 방지하기 위해 낙관적 락(`@Version`) 또는 비관적 락을 적절히 적용한다.
- 모든 API 응답은 공통 응답 포맷(성공/실패, 에러 코드, 메시지)을 통일하여 프론트엔드가 일관되게 처리할 수 있도록 한다.
- 권한 분리(운영진/회원)는 Spring Security 기반으로 구현하며, 운영진 전용 API(매칭 확정, 코트 활성화, 퇴장 처리, 게스트 등록, 정모 종료 등)는 반드시 역할 기반 접근 제어(`@PreAuthorize` 등)로 보호한다.
- 기피 인원 데이터는 조회 권한을 철저히 제한하여, 당사자 본인과 운영진 외에는 절대 조회할 수 없도록 Service 레벨에서 필터링한다.

## 5. DB(PostgreSQL) 역할 필수 준수사항

- 스키마 설계 시 **성능을 최우선 기준**으로 삼는다. 정규화 원칙을 지키되, 자동매칭 엔진처럼 실시간 조회가 빈번한 영역은 과도한 조인을 피하기 위해 의도적인 비정규화(예: 세션 참가자 테이블에 현재 ELO 스냅샷 컬럼 보유)를 허용한다.
- 매칭 엔진, 현황판, 랭킹 보드처럼 조회 빈도가 높은 쿼리 패턴을 먼저 식별하고, 그에 맞는 인덱스(복합 인덱스 포함)를 반드시 설계 단계에서 함께 정의한다. 인덱스 없는 대규모 테이블 풀스캔이 발생하지 않도록 주의한다.
- 회원(영구 데이터)과 게스트(세션 한정 임시 데이터)의 생명주기를 명확히 분리하여, 게스트 데이터가 영구 랭킹 이력 테이블을 오염시키지 않도록 테이블 구조 자체로 경계를 강제한다.
- ENUM성 데이터(급수, 연령대, 성별, 매칭 상태 등)는 VARCHAR + CHECK 제약 조건 방식으로 관리하여 운영 중 값 추가/변경이 유연하도록 하며, 매직 스트링을 코드에 흩뿌리지 않고 설정 테이블(`grade_elo_base`, `age_group_bonus`, `club_settings`)로 관리한다.
- 자동매칭 제안(DRAFT) 상태의 데이터는 실제 확정 데이터와 동일 테이블 내 상태 컬럼으로 관리하되, DRAFT 상태 데이터가 누적되어 테이블이 비대해지지 않도록 일정 시간 경과 시 정리(batch cleanup)하는 정책을 함께 고려한다.
- 트랜잭션이 잦은 테이블(session_participants, matches, match_participants)에는 불필요한 외래키 체크나 트리거로 인한 성능 저하가 없는지 검토하고, 동시성이 높은 구간은 락 경합을 최소화하는 방향으로 설계한다.
- 대용량 이력 데이터(elo_history, session_results, monthly_ranking_snapshots)는 조회 패턴(기간별 조회, 회원별 조회)에 맞춰 파티셔닝이나 아카이빙 전략을 사전에 고려한다.
- 모든 스키마 변경은 마이그레이션 도구(Flyway 또는 Liquibase)를 통해 버전 관리하며, 직접 운영 DB에 수동 DDL을 실행하지 않는다.

## 6. 산출물 체크리스트 (매 기능 구현 완료 시 자가 점검)

- [ ] 이 기능이 성능에 미치는 영향을 검토했는가(쿼리 횟수, N+1 문제, 불필요한 리렌더링 등)?
